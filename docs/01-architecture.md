# 01. 전체 아키텍처

## 1. 시스템 목표

1. **실시간성**: 새 뉴스/시세가 들어오면 수 초 내 지식 그래프에 반영.
2. **설명가능성**: 추천/답변에 항상 근거(뉴스, 수치, 날짜)를 연결.
3. **확장성**: 자산·소스·언어를 추가해도 스키마/파이프라인 변경 최소화.
4. **안전성**: 투자자문 리스크를 회피하는 정보제공형 설계.

## 3. 두 개의 처리 경로 (Lambda 유사)

| 경로 | 용도 | 지연 |
|------|------|------|
| **스트리밍(hot)** | 신규 뉴스/시세 → CDC → 그래프 즉시 반영 | 초 단위 |
| **배치(cold)** | 임베딩 재계산, 섹터 모멘텀 집계, 백필 | 분~시간 |

스트리밍이 "최신성"을, 배치가 "정확성/풍부함"을 담당한다. 둘 다 같은 Neo4j에 수렴한다.

## 4. 왜 이 기술들인가

- **CDC(Debezium)를 쓰는 이유**: 스크래퍼가 DB에 넣은 데이터를 폴링으로 다시 읽으면 부하·지연·중복 처리 문제가 생긴다. WAL 로그 기반 CDC는 **변경분만**, **순서 보장**, **at-least-once**로 전달한다. 또한 그래프 적재 로직과 수집 로직을 **느슨하게 결합(decoupling)**한다.
- **Kafka를 중간에 두는 이유**: 컨슈머가 죽어도 메시지가 보존되고(리플레이 가능), 나중에 "임베딩 전용 컨슈머", "알림 컨슈머" 등을 **추가만으로** 확장 가능.
- **Neo4j(그래프)를 쓰는 이유**: 금융 인사이트는 본질적으로 **관계 탐색**("이 뉴스가 어떤 종목·섹터·경쟁사에 영향?")이다. 관계형 조인보다 그래프 순회가 표현력·성능 모두 유리하다.
- **LLM 에이전트가 그래프를 도구로 쓰는 이유**: 그래프가 "검증된 사실"을 제공하므로 환각을 억제하고, 답변에 **근거를 인용**할 수 있다.

## 5. 컴포넌트 책임 분리

| 컴포넌트 | 책임 | 책임 아님 |
|----------|------|-----------|
| 스크래퍼/수집기 | 원천 수집 + staging 적재 | 의미 해석, 그래프 적재 |
| Debezium | 변경 캡처 + 전달 | 비즈니스 로직 |
| Pipeline consumer | 엔티티 해소·감성·임베딩·그래프 적재 | 수집, 사용자 응답 |
| Neo4j | 사실 저장·관계 질의 | 추천 정책 |
| Agent | 질의 계획·추천·자연어화·면책 | 데이터 수집 |

이 분리 덕분에 각 부분을 독립적으로 교체/확장할 수 있다(예: Neo4j→RDF 저장소, Debezium→Flink CDC).

## 6. 비기능 요구사항

| 항목 | 목표 |
|------|------|
| 뉴스→그래프 반영 지연 | p95 < 10s |
| 그래프 질의 응답 | p95 < 500ms |
| CDC 전달 보장 | at-least-once (멱등 MERGE로 중복 무해화) |
| 장애 복구 | Kafka offset/Neo4j MERGE로 재처리 안전 |
| 확장 | 컨슈머 그룹 수평 확장, 토픽 파티셔닝 |
